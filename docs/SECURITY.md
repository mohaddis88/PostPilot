# SECURITY.md — Security and data handling

Covers how PostPilot protects accounts, credentials, media and data. Companion files: THREAT_MODEL.md (what could go wrong) and SECURITY_CHECKLIST.md (what to verify before each milestone).

## 1. Principles
1. The browser is untrusted. The frontend never holds secrets and never decides who is allowed to do what.
2. Check authorization on the server, every request: user, then profile, then action.
3. Least privilege everywhere: database policies, Drive folders, OAuth scopes, Clawed tools.
4. Postgres is the source of truth for state. Redis is only queue and lock coordination.
5. Never log secrets. Logs get safe messages, raw platform payloads are stored redacted.
6. Fail visibly. A failed or uncertain publish is shown and recorded, not retried quietly.

## 2. Authentication and authorization
- Supabase Auth handles login and passwords. PostPilot stores no passwords itself.
- Authenticated user and publishing profile are separate ideas. The backend checks `authenticated_user -> allowed_for_profile -> requested_action` on each call, using the profile sent with the request, never trusting the UI's selection alone.
- Profile isolation has three layers: backend check (`post.profile_id == account.profile_id`), composite foreign keys in Postgres, and row level security on every table.
- Post and job states change only through backend code. The frontend cannot set a status.
- High-impact actions (publish now, reschedule, cancel, delete) need an explicit confirmation, including when requested through Clawed.

## 3. Data inventory
| Data | Sensitivity | Where it lives | Protection |
|---|---|---|---|
| Social OAuth tokens (access, refresh) | Critical | `social_accounts`, encrypted columns | Encrypted at rest with a server-side key, never sent to the browser, never logged |
| Supabase service role key | Critical | Server environment only | Never in frontend, repo or Clawed |
| Google service account credentials | Critical | Server environment only | Folder-scoped access, rotated if exposed |
| LLM API key | High | Server environment only | Never in `VITE_` variables; free tier means test data only |
| User account (name, email) | Personal data | Supabase Auth | RLS, minimal fields, not shown to other profiles' data views |
| Images and videos | Business confidential until published | Google Drive | Designated folders per profile, file ID stored in Postgres, no public links |
| Captions, drafts, schedules | Business confidential | Postgres | RLS by profile |
| Metrics and analytics | Internal | Postgres | RLS by profile, never mixed across profiles |
| Execution and audit logs | Internal, sensitive context | Postgres | Append-only in practice, no secrets, kept for history |

If real customer or staff personal data ever flows through the system, check Malaysia's Personal Data Protection Act obligations with the company before going live. This document does not replace that review.

## 4. Secrets management
- Secrets live in environment variables on the server (and in the Vercel and hosting dashboards), never in the repository.
- Only variables prefixed `VITE_` reach the browser, so only public values (project URL, anon key, API mode) use that prefix.
- `.env*` is in `.gitignore`. Only `.env.example`, with fake values, is committed.
- A key that was ever pasted into a chat, screenshot or commit is treated as exposed and rotated.
- Check the AI Studio export for leftover keys (`GEMINI_API_KEY`, `process.env`) before the first push.

## 5. Database (Supabase)
- Row level security is on for every table that is exposed through the API, with policies written for each operation the app uses.
- The service role bypasses RLS, so it is used only by the backend and workers.
- Tables hold references (Drive file IDs), not media.
- Idempotency keys have a unique constraint. Job state, leases and heartbeats are durable in Postgres.
- Migrations are versioned files with a test for each policy change.

## 6. File and Drive security
- A service account with access only to the designated folders (one set per profile). The backend checks that a requested file sits inside the right profile's folder before using it.
- Uploads are validated by extension, declared MIME type, real content (not just the filename), size and duration. Unexpected or executable types are rejected. Malware scanning is added where the hosting environment supports it.
- The browser never receives Google credentials. If a temporary file URL is needed, it is short-lived and generated by the backend.
- ffmpeg is invoked with an argument list, never through a shell string, and user-supplied filenames are never placed in commands. Output paths are generated by the server.

## 7. Social platform credentials
- Request the smallest scopes that work. Keep API versions and scopes in configuration.
- Refresh tokens on the server only. On failure, mark the account as needing reauthorization and tell the user in plain language.
- Revoke tokens when an account is disconnected.
- Mock adapters are labelled "Simulated" everywhere so nobody mistakes a test for a real publish.

## 8. Clawed and LLM safety
- Allowlisted tools only, all executed through the backend with normal authorization. No database access, shell, arbitrary HTTP, or credentials.
- Captions, files, web pages and platform replies are data. Instructions inside them are ignored.
- Responses use backend-calculated numbers and keep observed data, interpretation and suggested experiment separate.
- Free-tier LLM traffic may be used by the provider to improve its products. Use fictional captions until a paid or data-protected tier is chosen.

## 9. Logging and audit
- Audit events: login, profile selection, post create/edit/delete, schedule, cancel, publish attempt and result, token refresh, account connect/disconnect, Clawed tool use, manual retry.
- Each event records who, what, when, which profile, which post, which platform. Secrets and tokens are excluded.
- Errors shown to users are plain language. Raw payloads go to the execution log only, redacted.

## 10. Web application hardening
- Escape or sanitize all user text when rendering (captions, filenames, comments) to prevent XSS. No raw HTML injection.
- Restrict CORS to the real frontend origin. Use HTTPS only.
- Rate-limit the API, especially login, upload and Clawed endpoints. Limit upload size.
- Send security headers (Content-Security-Policy, X-Content-Type-Options, frame protections) from Vercel and the backend.
- Keep dependencies updated, commit lockfiles, and run an audit (`npm audit`, `pip-audit`) before releases.

## 11. Retention and deletion
- Media can be archived or deleted by policy. Post records, publishing history, metrics and audit logs stay for history.
- Deleting a draft moves it to Recently deleted for 30 days, then it is purged.
- Disconnecting an account revokes its tokens and removes the encrypted values.

## 12. If something goes wrong
1. Revoke or rotate the exposed key or token (Supabase, Google, platform, LLM).
2. Disable affected accounts in PostPilot and pause the scheduler if posts could go out wrongly.
3. Check the audit log for what happened and which profile was involved.
4. Fix, then record what happened and what changed.
